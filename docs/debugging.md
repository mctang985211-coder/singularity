# 故障定位与最小修复

目标与 spec 规范见 [spec-policy](spec-policy.md)。本页保留可复用方法；缺陷经过与旧实现从 Git 查证。

## 1. 找到规则的起点

先用实际触发说明输入、状态、操作和错误结果；区分可达产品问题、公开 API 缺口与理论构造。
沿公开端口找到最早让错误状态合法化的地方，修正该边界，删除补偿它的特殊分支。
队列只在实际异步提交边界串行化；读已验证投影不重复重放全库。涉及复杂度时量调用次数/状态转换，耗时作辅助证据。

## 2. 内存与业务事实

live handle/map 表示当前进程持有何种资源，不能表示 Task 已完成、Run 在执行或计划归谁。
已验证投影和性能缓存可以在内存中；正确结果必须可从准确事实及 DSH 来源重建。
恢复区分 working、submitted、settled；不能把所有 running 都送去重新验证，也不能由“最近 parent”恢复责任。

## 3. 正常推进与故障出口

计划发布、verified 结算后推进依赖，启动时显式恢复，是正常消费者。
异常后扫描不等于重试授权。运行时错误明确停止/报告；普通验收 fail 仅在冻结预算内启动同会话下一 Run。
已提交事实不因后续副作用失败而撤销；错误需指出阶段与已完成结果，不能让模型重提已结算 Run。
close/drain/flush 的失败保留可观察出口，资源只有一个 owner/disposer。

## 4. 定向反例与变异

1. 选一个承重的公开行为，写能区分正确与错误实现的正/负例。
2. 施加最小有效改动，确认改动命中待验证规则而非测试启动路径。
3. 跑最相关 spec/探针，核对失败指向目标行为，不能仅看退出码或任意失败标记。
4. 恢复源文件、保留必要回归；已有变异的编辑与 witness 由 mutation baseline 持有。

未触发先检查构造、可达性和覆盖；确无消费者的规则删除，有消费者但未被验证的行为补有效见证。
不为每个普通分支增加一份变异，也不把测试红灯当可达性证明。

## 5. 修复后连根清理

删被替代流程、无消费者字段、陈旧缺陷注释与重复 spec；需要函数时按真实责任提取，不包装错误旧流程。
注释只解释当前不能直观看懂的约束、宿主合同或算法理由，不保留逐轮辩护和修复日志。
更新当前合同、出口状态和必要证据；context 替换已关闭项，不继续追加历史。
