# tdd-seams.md —— E/F 的构建顺序：先认缝，再一个切片一个切片地写

来源：`mattpocock-skills-zh-CN/skills/engineering/tdd`（red → green loop 的 reference）。
本文件只记它与本项目**冲突或互补**的地方，以及 E/F 提议的缝（seams）。**缝没被确认之前不写任何 test。**

## 0. 一处必须先说清的冲突

你的指令是"**先写 spec 固定好想要的功能，再让人进去实现**"。引用的这份 skill 把那个顺序
**明确列为反模式**：

> **Horizontal slicing**：先写所有 tests，再写所有 implementation。批量 tests 验证的是*想象中的*
> behavior：你测试的是东西的 *shape*，不是 user-facing behavior；tests 会对真实变化迟钝，并在理解
> implementation 前承诺 test structure。改用 **vertical slices**：一个 test → 一个 implementation →
> repeat，每个 test 都是回应上一轮学习的 **tracer bullet**。

**冲突的解法（我提议这样理解你的意图）**，因为两者其实各自对了一半：

| 层次 | 谁先 | 为什么 |
|---|---|---|
| **缝**（公开边界、载荷形状、语义规则） | **先定，并且要你确认** | skill 明说："只测试预先认可的 seams。写任何 test 前，先写下要测试的 seams 并与用户确认。" 这就是你说的"先固定想要的功能"——固定在**缝**这一层。 |
| **每个缝的 spec 与实现** | **一个切片一次**：先写会红的 spec，再写刚好让它绿的实现 | 这就是你说的"先 spec 后实现"——在**切片**这一层成立。 |

所以最终顺序是：**认缝（含你签字）→ 按缝排优先级 → 每个缝走一遍 red→green → 全部绿之后统一 refactor**
（skill：refactoring 不属于 red→green loop，属 review 阶段）。

**与 `docs/spec-policy.md` 的关系**：完全一致。skill 的"好 test 只经 public interface 验 behavior"
就是我们那条"只锁调用方看得见的行为"；skill 的 seam 就是我们说的"公开表面"。
**但要加一条**：skill 的 seam 是"预先与用户确认过的边界"，比"调用方看得见"更严——
**没被确认的缝，不写 test**。

## 1. 从这份 skill 直接采用的四条

1. **红先于绿。** 先写会失败的 test，再写刚好够让它通过的代码；不预判未来的 test，不加投机功能。
2. **一次一个切片。** 一个缝、一个 test、一个最小实现。
3. **反模式清单当 review 项用**：
   - *implementation-coupled*：mock 内部协作者、测 private、走 side channel 验状态；特征是
     **行为没变而 refactor 后 test 红**（= `docs/spec-policy.md` §4 的"删掉它"）。
   - *tautological*：expected value 用和代码同样的方式算出来（`expect(add(a,b)).toBe(a+b)`、把常量
     断言成它自己）。**expected 必须来自独立来源**：已知正确的字面量、手算样例、或 spec。
   - *horizontal slicing*：见上。
4. **refactor 不属于 loop**，绿了之后单独一次。

### E1 的形状（**先定这个，再写第一条 test**）

**问题**：`acceptedAssetsBelow`（novelty 的历史输入）**没有承载它的事实**，而且它是 `MeasureSlice`
上的一个**注入端口**——端口的实现者自由发明约定，已经发明了两套（一套从 `pointer/switched` + 修订清单
推导，一套读探针自己协议里的 `assets/published`）。因为 `noveltyOf` 喂给 `selection`，两套约定能从同一条
日志得出两个胜者。

**选定：一个投影，一个所有者，输入全是冻结事实。**

```
publishedAssetsBelow(entries, environmentId, cutoff) -> readonly string[]
//   1. 按 seq < cutoff 折叠该 environment 的 pointer/switched，得到最后指向的 revisionId
//   2. 找到"选出提议了该修订的那个槽位"的 round/decided（跨 subject，全日志扫）
//   3. 该槽位的 candidate/submitted 声明的 edits 的 asset 类，去重后按序
```

**为什么不是"加一条事实"**（被否决的备选）：那要么给 `environment@2` 加成员（`environment@3`），
要么给 `release@1` 加 kind（`release@2`），而它记的东西**完全可从已冻结的事实推出**——本项目自己的
规矩是"派生量永不持久化"（门禁 `derived-not-persistable` 就是这个意思）。R03 要防的是**按今天的 head
重算**，而这个投影的每个输入都在 `cutoff` 之下、永不改变。

**为什么两套约定是缺陷而不是自由**：因为推导**没有所有者**。修法不是"再加一套更好的约定"，而是
**把端口拿掉**——`MeasureSlice.acceptedAssetsBelow` 不再由调用方注入，改由这一个函数提供，于是
"accepted"只有一个定义，而且它有 spec 和变异证明钉住。

### E1 形状的三处修正（**E1 切片实现时发现缝本身有错**）

这正是 red→green 该产生的反馈：实现方按**签字原文**实现，然后指出原文自相矛盾。

| # | 问题 | 决定 |
|---|---|---|
| a | 第 2 步写"跨 subject，全日志扫"，与本文档"每个输入都在 `cutoff` 之下、永不改变"**自相矛盾**：cutoff **之上**的一次选举仍能给冻结历史添资产类（R03 从选举而不是 head 钻回来）。而且 `release.publish` 只需要批准、不需要轮次，所以"每次发布都是某轮胜者"不成立，两种读法会分叉。 | **第 2 步也按 `seq < cutoff` 界定。** 于是每个输入真的都是冻结的，那句话不再是空话。 |
| b | 行文说"资产类**绑定到修订内容摘要**"，但签名给的形状只按 `(environmentId, revisionId)` 配对，**从不比较摘要**：一个 id 对、内容不对的槽位，它声明的资产类照样被算进去。 | **按 `sameRevision` 比较三元组**（id + 摘要 + environment）。内容寻址的意义就在这里，签名里的措辞也是这么写的。 |
| c | **两轮各自选出"提议同一个 head 修订"的槽位、而两次声明的 edits 不同**时未定义；"first match only" 也能通过当时的 spec。 | **取并集、去重、按轮与声明顺序**，并**为它补一条 spec**（把自由选择变成被钉住的行为）。并集也更保守：不会把已经走过的资产类算成新。 |

**另外记账**：这个投影每次调用要重折一段前缀 + 整个 strategy 协议，而 `decideRound` 会投影两次。
签名（`entries, environmentId, cutoff`）决定如此，可接受；轮次变长之前要知道。

**这条缝的 spec 要断言什么**（调用方看得见的行为，一条一件）：
1. head 指向的修订所对应槽位的 asset 类被算作已接受；cutoff 之下未发生指针切换时为空。
2. 指针切换发生在 `cutoff` **之后**时，它指向的资产**不算**已接受（历史不被后续 head 改写，R03）。
3. 同一修订被两轮各自选中时不重复计数。
4. 一个 `pointer/switched` 指向的修订在本日志里找不到提议它的槽位时，**不猜**——返回不含它，且这不是拒绝
   （历史上可能有别处创建的修订）。
5. （修正 a）**`cutoff` 之上的选举不贡献**资产类。
6. （修正 b）head 修订 id 相同但**内容摘要不同**的槽位，其声明的资产类**不算**已接受。
7. （修正 c）两轮各自选出提议同一修订的槽位、edits 不同时，取**并集**。

**expected 的来源**（反 tautological）：用手算的字面量资产类列表，不用被测函数算。

## 2b. E3 的形状（**已定，去写它的 spec**）

**问题（R01 原文）**："所有槽位都有完成/拒绝/未测原因后结案；无胜者也要记录本轮轨迹。"
今天 `round/decided` 只要求**每一个已提交的槽位**有 outcome。于是
**`round/opened` 声明了、但没人提交的槽位根本没有 outcome，也不出现在任何理由里**——
"所有槽位结案"这句话现在是假的。保留探索槽尤其明显：它按设计就该允许空着。

**选定：结案覆盖声明的槽位，而不是提交的槽位。**

- `round/decided` 的 reducer 要求 outcomes **恰好覆盖 `[0, candidates)` 全部槽位**，
  缺一个就拒绝（`illegal-transition`，消息里点出缺哪个槽位号）。
- 没有任何提交的槽位，其 outcome 的 `admitted: false` 且理由**具名**（例如
  "no candidate was submitted to this slot"）。于是"未测"是一个**事实**，不是沉默。
- `winner` 仍必须是某个 `admitted: true` 的槽位，或 `null` ✓ 不变。

**这条缝的 spec 要断言什么**（一条一件，expected 用手写字面量）：
1. 某个声明槽位无人提交时，`round/decided` 被拒绝，且理由点出那个槽位号。
2. outcomes 覆盖全部声明槽位时结案成功，未被提交的槽位带具名理由。
3. 一个 `candidates: 2` 而只有槽位 0 被提交的轮次，结案后**仍**只有提交过的槽位能当胜者。
4. `explorationSlots` 保留槽空着**不是**结案失败的理由（空着是合法的，只是要被记下来）。

**为什么不是"加 closure 成员"**：`winner` 已经承载了"有没有胜者"；再加一个同义成员会让
"有胜者却有 closure=stalled" 这种不一致状态变成可表达的。**能让不可能状态变成可能的字段不要加。**

## 3. 走法（每个缝一遍）

1. 写这条缝的 spec：**只经公开边界**，expected 来自独立来源（手算数、已知正确的字面量、协议冻结文本）。
2. 跑它，**看着它红**，把红的原因记下来（红的理由必须是"功能还没实现"，不是"接口不存在"）。
3. 写刚好让它绿的实现。不加未来要用的成员、不为预判的 test 留钩子。
4. 跑全量：`tsc`、`npx vitest run`、`node scripts/gates.mjs`。
5. **变异证明**：把这条规则的那一行关掉，确认刚才的 spec 红（`docs/debugging.md` §4）。
6. 下一个缝。

全部绿之后：一次独立的 refactor + review（skill：refactor 不属于 loop）。

## 4. E2 的形状（**已定：一个新 kind，不新协议**）

R08 最后一段：**"只证明 Run 钉住某 revision，不能证明其中某 Skill 或 Tool 被使用。"**

**先问"有没有更简单的"**：消费是"某次 run 用了某个方法"。run 本来就是 **task 协议**里的事实，
所以**新开一个 `consumption@1` 协议是多余的**——那会重复 `requireRun`、责任门、输入绑定、
投影与视图。**放进 `task@5` 一个 kind**，其余全部复用。

```ts
'method/consumed' { runId, revision: RevisionRef, method: string, source: string }
```

- **subject = task id**（和 run 同一条链），发射者是 **`AGENT_ROLE`（'runtime'）**——
  即"跑东西的那套装置"，不是候选自己的 agent。**自述不算凭据**：`source` 必填且非空，
  它回答"这个断言从哪来"。
- reducer 规则（同 subject，纯判）：run 必须存在；**`revision` 必须等于该 run 当初钉住的那个**
  （`sameRevision`）——于是"用了一个我没被钉到的方法版本"不可表达；`(runId, method)` 只能消费一次，
  第二次是 `evidence-conflict`；`source` 非空。
- **一个投影，一个所有者**：`unconsumedMethods(entries, environmentId, revisionId, declared, cutoff)`
  —— `declared` 是**该修订声明的方法名**，由**部署**从它自己的清单格式里读出来（我们的协议不规定
  别人的清单长什么样）；投影只负责比较"声明了哪些"与"截止之下有哪些消费事实"。
  **这就是"用固定端口交流"**：清单格式留在部署侧，比较规则在我们侧，各有各的 spec。
- 版本：`task@5`，因为**加 kind 就是改变 kind 集合**；v1–v4 按 `version-mismatch` 具名拒绝。

**spec 要断言什么**：1) 消费事实记在 run 上、且 revision 与 pin 不符时被拒；2) 同一 `(runId, method)`
第二次被拒；3) `source` 为空被拒；4) 投影把"声明了但没有消费事实"的方法点出来；
5) 截止之后的消费事实**不算**（历史冻结）。

## 5. F 的形状（**已定：F 新增 0 个协议**）

**先问"有没有更简单的"**：F 的退出条件是"恢复/边界行为满足新契约，真实质量和成本满足冻结标准"——
这是**取证**，不是造机制。而我原本记的三个缝（F1/F2/F3）全都已经被现有东西覆盖：

| F 要的 | 已经有的东西 | 结论 |
|---|---|---|
| 冻结领域任务集 | **一个 fixture 文件**：任务（goal + 契约 + 判据）+ 冻结的模型配置与预算。它的**内容摘要**就是这次对照的身份 | **不新协议** |
| 同口径对照 | **`measure@3` 的一次 evaluation**：baseline = H0 的修订，candidate = 发布的方法。口径摘要已经覆盖模型/工具/条件/输入 | **不新协议** |
| 行为回归 | **既有探针**：`control-probe` / `recovery-probe` / `slice-b` / `cd-probe` | **不新代码** |

所以 F 的交付物是：**一个 fixture + 一个对照探针 + 一份证据文档**。**一个协议都不加。**

**F 的探针要断言什么**（expected 来自 fixture 与手算，不由被测函数算）：
1. 同一任务集在 H0 与发布修订下各产生一次 evaluation，两侧修订与口径摘要如实记录；
2. 被反复反馈给 proposer 的集合与**未使用的留出集**分别记录（R08：不能把已进入搜索的数据
   继续称作留出证据）；
3. 同一截止范围重放得到同一对照结论；
4. 既有四个探针在新契约下全绿（这就是"行为回归"）。

**F 明确不做**：删除旧栈、把旧栈的数据迁过来、通用沙箱、group/router、任何新的轮次编排。
"部署替代"的**证据**是上面四条，不是一次不可逆的切换。
