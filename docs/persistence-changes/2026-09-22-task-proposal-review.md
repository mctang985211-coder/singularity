# 2026-09-22-task-proposal-review

## Summary

Adds the T2/T3 proposal surface to the `task/event` root: four new kinds (`TaskProposalSubmitted`, `TaskProposalDecided`, `TaskProposalPhaseChanged`, `TaskProposalAdmitted`), the record types behind them (`TaskProposal` with `TaskProposalPolicy`, `TaskProposalStatus`, `TaskProposalDecision` and `TaskProposalChild`, `TaskProposalDecisionClaim`, `TaskProposalPhaseChange`, `TaskProposalConsumption`, `TaskProposalReviewContext` with `TaskProposalVerifierIdentity`), the identity helpers for the two contexts a review binds (`admissionContextDigest`, `reviewContextDigest`, plus `capabilityManifestDigest` for the manifests a batch resolved), the proposal id derivation (`taskProposalId`), and one new optional `TaskSnapshot` member, `proposals?: TaskProposalIndex` (a proposal's index by id, by request key, and by parent task). A proposal carries its batch **in full** — `TaskProposal.batch` is one `TaskProposalChild` (a complete normalized `TaskContract` plus `dependsOn`, `decomposable`, `requiresIndependentAcceptance`) per identity child, in the same order — because §5 requires an approval request to show every child's goal, criteria, assumptions, constraints, dependencies and capabilities, and §7 requires graph/canvas to render waiting, rejected and admitted proposals from saved facts; the reducer refuses any batch that disagrees with the identity it accompanies, so content and commitment cannot diverge. `TaskService` gains `submitProposalIn`, `decideProposalIn`, `changeProposalPhaseIn`, `consumeProposalIn`, and `admitBatchIn` gains one trailing optional parameter carrying the proposal consumption — the whole batch and the record of which proposal it consumed land in one commit. No envelope, no existing event payload, and no existing reducer rule changes. This change lands the store-side contract of the T2/T3 delivery group (construction guide `docs/task-contract-construction-guide.md` §5–§7); the runtime that proposes, decides and consumes — the policy gate, the approval channel, the post-approval re-check and the recovery handoff — was a later stage of the same group, and it landed in the same working tree (see [Verification](#verification) for the final all-green numbers, and `docs/singularity-harness-guide.md` §5.10 for the runtime's own contract).

<a id="registered-shapes"></a>
## Registered shapes

| Root | Payload | Current shape |
|---|---|---|
| `event:task/event` | `TaskEvent` | Unchanged declaration; the union gains `TaskProposalSubmitted`, `TaskProposalDecided`, `TaskProposalPhaseChanged` and `TaskProposalAdmitted` members |

The four new members, declared in `task/src/types.ts` with JSDoc (as every member must be) and typed by `task/src/proposal.ts`:

- `TaskProposalSubmitted: { proposal: TaskProposal }` — `TaskProposal` is `{ proposalId, requestKey, supersedes?, status: TaskProposalStatus, policy: 'off' | 'all', identity: DecompositionIdentity, batch: readonly TaskProposalChild[], proposalDigest, admissionContext: AdmissionContext, admissionContextDigest, reviewContext: TaskProposalReviewContext, reviewContextDigest, createdAt, updatedAt?, decision?: TaskProposalDecision, consumption?: TaskProposalConsumption }`. `identity` is T1's `DecompositionIdentity` (store, parent task, parent run, caller, contract version, reason, complete ordered children); `proposalDigest` is `decompositionDigest(identity)`. `batch` is the reviewed content: one `TaskProposalChild` = `{ contract: TaskContract, dependsOn: number[], decomposable: boolean, requiresIndependentAcceptance: boolean }` per `identity.children` entry, in the same order — the same four items T1's `normalizeDecomposition` produces per child, so a caller that already holds a normalized batch passes its children straight through.
- `TaskProposalDecided: TaskProposalDecisionClaim` — `TaskProposalDecision` (`{ outcome: 'approved' | 'rejected' | 'cancelled' | 'expired', proposalDigest, admissionContextDigest, reviewContextDigest?, decidedBy, decidedAt, reason? }`) plus the `proposalId` the decision is about.
- `TaskProposalPhaseChanged: TaskProposalPhaseChange` — `{ proposalId, to: 'ready' | 'pending_review' | 'stale', reason? }`.
- `TaskProposalAdmitted: TaskProposalConsumption` — `{ proposalId, proposalDigest, reviewContextDigest, batchId, childTaskIds, admittedAt, reason? }`.

`TaskProposalReviewContext` is `{ capabilityManifestDigest: string, verifiers: TaskProposalVerifierIdentity[] }`, where a verifier identity is `{ verifierId, version?, configurationDigest? }`. Its digest (`task/src/proposal.ts:reviewContextDigest`) normalizes the verifier list to ascending `(verifierId, version, configurationDigest)` before hashing, so the same set of judging instances resolved in two orders is one identity; `admissionContextDigest` hashes `AdmissionContext` with `canonicalize`, and `capabilityManifestDigest` hashes the batch's resolved manifests in batch order. All three use the T1 canonicalization discipline (sorted object keys, arrays in order, SHA-256) and are pinned by fixed-vector tests whose expected digests were computed outside the repository.

Reducer discipline (`task/src/service/state.ts`):

- `TaskProposalSubmitted` (`submitProposal`): the record must be well formed — a non-empty id and request key, a birth status that matches the policy (`off → ready`, `all → pending_review`), a `supersedes` naming an existing proposal and never itself, an identity whose contract version this build knows and whose children carry digests, dependency indices and booleans, a parent task the store holds, a closed review context, and three digests that really are the digests of the data they accompany (a mismatch is refused by name, which is what keeps a later approval binding meaningful). The batch is then checked against the identity it accompanies (`assertProposalBatch`): one entry per identity child in the same order, a closed field set per entry, a contract this build can read (version, non-empty lists, string objective — the same helper the task-side contract check uses), a dependency list of non-negative indices, both flags boolean, and then the correspondence itself — `contractDigest(contract)` equal to the identity child's `contractDigest`, and `dependsOn` / `decomposable` / `requiresIndependentAcceptance` equal item by item. A content↔identity disagreement is refused with the field named and zero writes, so an approval can never be displayed one batch and admitted from another. The proposal id and the request key must be free; a repeated request key is refused rather than silently aliased, so one key names at most one proposal. Nothing else in the store changes: a proposal creates no task, admits no child and marks no parent decomposed.
- `TaskProposalDecided` (`decideProposal`): the outcome must be one of the four, the proposal must exist and be named by the envelope's task, `proposalDigest` and `admissionContextDigest` must equal the stored ones, an approval must carry the `reviewContextDigest` it was decided against (and a present one on any outcome is checked), the decider and decision time must be non-empty, an expiry must state its reason, and the outcome must be legal from the current status (`approved`/`rejected` only from `pending_review`; `cancelled`/`expired` also from `ready` and `approved`). A second decision, an approval of a policy-off batch, and an approval of a proposal that already lost its approval are transition refusals.
- `TaskProposalPhaseChanged` (`changeProposalPhase`): the target must be one of `ready`, `pending_review`, `stale`, the source status must be legal for it (`ready → pending_review` for a deployment tightening, `approved → ready` for a passed re-check, `ready|approved → stale` for a failed one), and a `stale` marking must name what changed.
- `TaskProposalAdmitted` (`admitProposal`): the proposal must exist, the consumption must carry the stored `proposalDigest` and `reviewContextDigest`, the batch id that belongs to this parent (`b-<parentTaskId>`), at least one distinct child task id, each of them a task the store really holds as a child of that parent, and an admission time; the status must be `ready` — an approval alone never admits, because §6 puts the re-check between approval and admission and `approved → ready` is where that re-check is recorded. A second consumption is refused, so one proposal can never become two batches.
- `TaskStarted` / `TaskCreated`: unchanged. A proposal is never a task, and no task field was added.

Service entries (`task/src/index.ts`): `submitProposalIn` writes one `TaskProposalSubmitted` event whose envelope names the proposal's parent task; `decideProposalIn`, `changeProposalPhaseIn` and `consumeProposalIn` each read the parent task from the store's proposal index first (an unknown proposal is refused before anything is queued) and then write one event; `admitBatchIn` takes an optional trailing `TaskProposalConsumption` and, when given, requires it to name exactly that batch's children in batch order and appends `TaskProposalAdmitted` to the same commit — so "this proposal was consumed and these are its tasks" is one durable fact, and a crash after admission is recoverable from the log without admitting a second batch.

The declaration-level fingerprint does not move: digests cover event name + payload type text (`TaskEvent`), and the four new kinds live inside the transitively referenced `TaskEventPayloads` union. Per this directory's README, such changes are acknowledged by record alone; the sibling `.schema.json` therefore repeats the unchanged after digest — the same situation as `2026-09-22-a3-coordination-phases`, `2026-09-22-run-provider-binding` and `2026-09-21-task-contract-normalization`.

`TaskSnapshot` (not an event root; no fingerprint covers it) gained the optional member `proposals?: TaskProposalIndex` = `{ all, byId, byRequestKey, byParentTask }`. It is optional at the type level because snapshots are also built by hand elsewhere in this workspace — a verifier's selftest store view (`verifier/src/index.ts:sampleSnapshot`) and several unit-test helpers — and those literals predate proposals; making it required would have broken their type checks without changing anything they read. A snapshot produced by this build's reducer always carries it, empty members included; an absent index means "this reader cannot see proposals" and is refused by the reducer (`task: snapshot carries no proposal index`) rather than read as "the store holds none".

<a id="lifecycle-and-binding"></a>
## Lifecycle and binding

The status table (`TaskProposalStatus`) is the contract this change encodes, and every legal edge has exactly one event behind it:

| From | To | Event |
|---|---|---|
| — (birth, policy `off`) | `ready` | `TaskProposalSubmitted` |
| — (birth, policy `all`) | `pending_review` | `TaskProposalSubmitted` |
| `ready` | `pending_review` | `TaskProposalPhaseChanged` (deployment tightened to `all` before admission) |
| `pending_review` | `approved` / `rejected` | `TaskProposalDecided` |
| `ready` / `pending_review` / `approved` | `cancelled` | `TaskProposalDecided` |
| `ready` / `pending_review` / `approved` | `expired` | `TaskProposalDecided` (a late approval after the parent run ended — an invalidation, never a dispatch) |
| `approved` | `ready` | `TaskProposalPhaseChanged` (post-approval re-check passed) |
| `ready` / `approved` | `stale` | `TaskProposalPhaseChanged` (re-check failed; a capability, budget or verifier change) |
| `ready` | `admitted` | `TaskProposalAdmitted` |

`rejected`, `cancelled`, `stale`, `expired` and `admitted` are terminal and the records are kept: §6's revision path is a new proposal with a new key and a `supersedes` reference, never an edit of the refused one. Two rules are deliberately stricter than a naive reading of the diagram, and the JSDoc on `TaskProposalStatus` states both: an approval alone never admits (admission happens from `ready`, so the re-check is a recorded fact rather than an implied one), and a waiting proposal is never released by a policy change to `off` (§5: only tightening is allowed).

What a waiting proposal holds is the batch itself. The identity is the commitment — its per-child `contractDigest` is the digest of the contract stored beside it — and the reducer enforces that correspondence on submission, so the content a reviewer (or a canvas, or a resumed approval request after a restart) renders is the content the approval binds and the content admission will create. The identity is derived from the content, not the other way round: `proposalId` and `proposalDigest` are computed from `identity` alone, so a batch that disagrees with the identity it accompanies is refused rather than hashed into a new id.

<a id="compatibility"></a>
## Compatibility

`same-version` per the fixed rules: an ordinary added event type and added optional properties are both minimum-decision cases, four times and once respectively.

New build reading old records is fully compatible. An old store contains no proposal events and no `proposals` snapshot member: replay applies the same events to the same statuses, the snapshot's index is simply built empty by the reducer, and every new reducer rule is reachable only through a new event. The one existing behaviour this change touches is a refusal already in place — `TaskSnapshot`'s new member is optional, so the hand-built snapshots in `verifier`, `agent-singularity` and `agent-runtime` type-check unchanged, and `admitBatchIn`'s new parameter is trailing and optional, so the runtime's existing call site is unaffected. Historical tasks are not held to the new review rules: a proposal is a separate record, so a task created before this build has no proposal to be pending and can still be replayed, verified and reviewed exactly as before (§7: new review rules apply to new proposals only).

`TaskProposal.batch` is required rather than optional, deliberately: `TaskProposalSubmitted` is itself a new event type, so no stored record can predate it and there is no older shape to keep readable, while an optional batch would let a writer store an identity with no content behind it — exactly what §5's display requirement and §7's "display from saved facts" rule out. The fixed rule that makes an added *required* property a `version-bump` case governs a property added to an event body that already existed; this property is part of an event body this build introduces, so the added-event-type rule (`same-version`) decides it.

An old build opening a store that contains these events refuses it, by name, at replay: `TaskState.apply` is fail-closed and throws `task: unknown event kind "TaskProposalSubmitted"` (and likewise for the other three). The envelope's `ignorable: true` only lets a build skip an unknown event *type*; it does not cover an unknown kind under the already-known `task/event` type. This is the intended fail-closed behaviour — the record does not claim older readers can ignore the addition. Writer and reducer ship together, and a task store is scoped to one root session, so in normal operation a single store is never replayed by mixed-version code. The external Evolution ledger (`proposals.jsonl`) is untouched: this proposal record is the task store's own event-sourced data, deliberately not an `EvolutionProposal` and not a side JSON file (§7).
