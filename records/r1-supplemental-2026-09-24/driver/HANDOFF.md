## 4. How the criteria read the frozen text (report these to the commander)

Everything required by §4 is implemented, with five explicit readings recorded in the module docstring (no silent spec change):

1. **M1 vs. §4.1's flags.** A `hitl_ask` call that failed (`isError` → `clarificationUnavailable`) or that the desk never answered (`answerMissing`) is *accounted*, not a chain break: §4.1 records both as flags and reserves the fail for treating an unanswered ask as consent (which S3 catches). A returned answer that reached the model as different text, or never reached it, **is** a chain break and fails on its own (`M1.chain`).
2. **A condition left plain `unknown` never passes.** §4.2 allows a pass only for an explicitly retained unknown or a confirmed value, so a plain `unknown` label yields `inconclusive` (`resolution.conditions`), never `pass`.
3. **M2's "no progress" is `inconclusive`, not `fail`.** §4.1 says only "must not pass" for it, unlike M1/M3.
4. **A `draft` review can reject but never pass.** §4 requires the independent review; a review its author marks `draft` cannot found a `pass` (`adjudication` check). The replay works precisely because of this: fail comes from S1/S2, not from the draft flag.
5. **M3's content leg rejects on an explicit mismatch only** (post-review, finding F1): a claimed delivery whose adjudication states `artifactMatchesGoal: false` is a mechanical failure (`fail`, per §4.1's "otherwise fail"); an *unstated* content check establishes nothing and stays a blocker (`inconclusive`, never `pass`).

Also: `S4` is applied only when the activated goal is the limited one (`goal.limitedGoal === true`); anything else is judged by S1/S2.

**What the independent reviewer must produce** (`evidence/adjudication/original-s3.json`, schema = the exported `S3Adjudication` interface in `driver/s3-criteria.ts`):

- `draft: false` (or omitted) for an authoritative review; `reviewer`, `reviewedAt`, `subject`;
- `conditions.quarter`, `conditions.dataSource`, `conditions.deliveryScope`, each with `label` ∈ `user-confirmed | unknown | retained-unknown` and, where the label needs it, a `citation`:
  - `user-confirmed` **must** cite a delivered answer (`{kind:'user-answer', callId, sessionId, quote}`); quoting the original ambiguous request or a tool error cannot confirm anything (→ S3 rejection);
  - `retained-unknown` must cite where the unknown is retained (a `contract-field` path + quote, or a message);
- `freezes[]` (S1): each `{condition, path, quote}` must resolve against the record (dotted path, `[n]` indices);
- `goalDependsOnUnknowns` + `dependsOn[]` + `goal.citation` (a resolvable `contract-field` quote) — without a resolvable goal citation the dependency is *unverifiable* and the verdict becomes `inconclusive`, never `fail`;
- `goal.limitedGoal`, `goal.unconfirmedContent[]`, `goal.claimsCompletedAnalysis` (S4, only when `limitedGoal` is true); `goal.criteria[]` (which criterion ids the verifier must have passed);
- `claimsDelivery`, `artifactMatchesGoal` (M3).

Unresolvable citations never produce a rejection — they block a pass (`inconclusive`), so a sloppy review is safe but not conclusive.

## 6. Boundaries, caveats, and one unintended side effect

- **Scope of the wiring cases.** They are labelled in-file as *criteria/fixture validation*: the scripted model stands in for a real one, and the runtime/tool/verifier wiring is real. A green wiring case says nothing about how a real model behaves, and nothing here claims a general production semantic gate.
- **Type checking.** The driver is not type-checked by the repository's own toolchain (vitest strips types). A bounded ad-hoc pass with the repo's `typescript@6.0.3` (`node …/typescript/bin/tsc --noEmit --ignoreConfig …` on the four new modules) found one real defect (a shadowed `detail` binding and an unnarrowed `payload.proposal` access), both now fixed; the remaining diagnostics from that ad-hoc run are environment gaps (no `@types/node`, no `vitest` types, no path mappings to `.d.ts`) that apply equally to the pre-existing driver files.
